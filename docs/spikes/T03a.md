# T03a — Streaming a growing file

Spike date: 2026-10-12. Spike code: `spikes/t03a/` (ignored, not merged).

## Question

Can the api serve an audio file while the worker is still writing it to `/staging` so that ExoPlayer (Media3) and third-party OpenSubsonic clients start playing quickly? We also wanted to know:

- what happens on seek and on a failure mid-stream;
- which response strategy works best: chunked with no `Content-Length`, an estimated `Content-Length`, or an exact `Content-Length` with Range;
- which container works: Opus in WebM or Ogg, or AAC in M4A (plain, faststart, fragmented).

## Setup

- **Audio**: 3-minute stereo tracks generated with ffmpeg 8.1 (a sine tone plus noise; no YouTube). The variants:
  - `opus_cuesfront.webm`: Opus 160k, Cues before the Clusters (`-cues_to_front 1`). This is the layout of YouTube itag 251.
  - `opus_cuesend.webm`: Cues at the end, with the SeekHead pointing at them (ffmpeg default).
  - `opus.ogg`.
  - `aac_moovend.m4a` (ffmpeg default) and `aac_faststart.m4a` (`+faststart`).
  - `aac_frag.m4a`: fragmented MP4 with `empty_moov`, no `sidx`.
  - `aac_dash.m4a`: fragmented MP4 with a global `sidx` at the front. This is the layout of YouTube itag 140 before yt-dlp's `FixupM4a`.
  - Sizes are 2.6–2.9 MB each.
- **Server**: FastAPI + uvicorn (the stack the api uses). `GET /stream/{name}` starts a simulated writer that copies the finished file into a staging file at a set rate in 8 KiB writes. This is how yt-dlp fills its `.part` file: a sequential HTTP download of a fixed file. The response tails the staging file (`pread` what is there, wait on an event otherwise). Options:
  - `mode=chunked`: no `Content-Length`.
  - `mode=length`: the exact final size is sent up front.
  - `range=serve`: answers `206` with `Content-Range: bytes a-b/total` and waits for bytes that are not written yet.
  - `range=ignore`: answers `200` and ignores Range.
  - `fail_at=N`, with `fail=abort` (raise in the generator, so the connection drops without a final chunk) or `fail=eof` (end the body cleanly).
- **Rates**: 20 000 B/s (about real time for 128–160 kbit/s), 65 536 B/s and 1 MB/s.
- **ffmpeg/ffprobe/ffplay** (libavformat 62) as an mpv-like third-party player. We measured the wall time of `ffmpeg -i URL -frames:a 1 -f null -`, which is the time until the first decoded audio frame.
- **Media3 1.11.1 on the plain JVM**, with no emulator and no Robolectric (`-Xmx64m`). A harness replays exactly what `ProgressiveMediaPeriod.ExtractingLoadable.load()` does:
  - it uses `BundledExtractorsAdapter` with the Matroska, fragmented MP4, MP4 and Ogg extractors;
  - each `DataSpec` carries the same flags ExoPlayer sets (`FLAG_DONT_CACHE_IF_LENGTH_UNKNOWN | FLAG_ALLOW_CACHE_FRAGMENTATION`, value 6, checked in the 1.11.1 bytecode);
  - it reopens the source with a Range request whenever the extractor returns `RESULT_SEEK`;
  - the data source is `DefaultHttpDataSource` (8 s timeouts), with or without `CacheDataSource` over `SimpleCache`;
  - a few `android.*` classes are replaced by small JVM stubs.

  It reports the time to the `SeekMap`, the time to the first sample (where a decoder could start), every Range request it makes, and what ends up in the cache. OkHttp 4.12 was tested separately for truncated bodies, because the Android app will use OkHttp.
- The playback-level behaviour (seek, retry, live detection) comes from reading the Media3 1.11.1 source: `ProgressiveMediaPeriod`, `DefaultLoadErrorHandlingPolicy`, `DefaultHttpDataSource`, `CacheDataSource` and `CacheDataSink`.
- Machine: a local loopback, so network latency is about 0. The numbers below are what the streaming layer adds. yt-dlp start-up and YouTube's time to first byte are measured in T03c.

### Other measurements

- **Full play-through while growing.** ffmpeg decoded the whole of WebM, Ogg and fMP4 while the files were being written, with no errors. RSS was about 65 MB. Media3 read all 9001 Opus samples (0–180 s) of `opus_cuesfront.webm`.
- **Seek with no Range on a chunked stream.** We ran ffmpeg with `-ss 120` at 64 KB/s, which takes about 41 s to download the file. The first frame arrived after 28–30 s for WebM, fMP4 and Ogg alike: ffmpeg reads and discards until the download reaches 120 s.
- **Range ahead of the writer.** With an exact length and `range=serve`, a request for `bytes=2270000-` (about 150 s into the track) returned `206` headers in 0.01 s. The body started when the writer reached that offset: about 34 s at 64 KB/s and about 2.3 s at 1 MB/s.
- **Media3 seeks to bytes that are not written yet.** Media3 then waits with no data. With `DefaultHttpDataSource`'s default 8 s read timeout, this ended in a `SocketTimeoutException` in every "stalls" row above.
- **Range headers sent by clients.** ffmpeg/ffplay (`Lavf`) always sends `Range: bytes=0-`. Media3 sends no Range at position 0 with an unknown length. Media3 always sends Range when it resumes or seeks.
- **SimpleCache.** We played `opus_cuesfront.webm` at 1 MB/s through `CacheDataSource`, then replayed it with the server unreachable:

| First play | Bytes cached | Stored length | Offline replay |
| --- | --- | --- | --- |
| chunked (flags as ExoPlayer sets them) | **0** | unset | **fails** (connection refused) |
| exact `Content-Length` | 2 723 039 (all) | 2 723 039 | plays all 9001 samples in 0.14 s |
| chunked, with `FLAG_DONT_CACHE_IF_LENGTH_UNKNOWN` cleared | 2 723 039 | 2 723 039 | plays all |

- **Failure mid-stream at byte 300 000** (writer stops; the server either aborts or ends the body cleanly):

| Response | Server ending | curl | OkHttp 4.12 (Android stack) | JDK `HttpURLConnection` (JVM only) |
| --- | --- | --- | --- | --- |
| chunked | abort (no final chunk) | exit 18, 0.37 s | `EOFException`, 0.40 s | `IOException: Premature EOF`, 0.41 s |
| chunked | clean end | **exit 0** (looks complete) | **clean EOF** | clean EOF |
| exact length | abort | exit 18 | `ProtocolException: unexpected end of stream` | silent EOF after about 30–40 s |
| exact length | clean end (h11 refuses it and closes) | exit 18 | `ProtocolException` | silent EOF |

## Findings for ExoPlayer / Media3

1. **The container decides everything.** Progressive playback of a growing file works only when everything the extractor needs at the start is at the front of the file:
   - WebM with Cues at the front;
   - fMP4 (with or without `sidx`);
   - faststart MP4;
   - Ogg, only when the length is unknown.

   Any layout that makes the extractor seek forward at start-up issues a Range request beyond the written bytes, and playback stalls until the download finishes. This happens with Cues at the end of a WebM (Matroska follows the SeekHead even on a chunked stream), with the moov at the end of an M4A, and with Ogg when the length is known (`DefaultOggSeeker` reads the last page to get the duration).

   YouTube's raw audio formats are expected to be in the good layouts: itag 251 as WebM with Cues at the front and itag 140 as DASH fMP4 with a `sidx` (per YouTube's DASH `initRange`/`indexRange`). **This spike did not measure it**: every test file here was generated with ffmpeg, so the layout of real 251/140 files must be confirmed with `ffprobe` on downloaded files (T03c's pending download run) before T08/T16 rely on it. If 251 ever ships with Cues at the end, it must only be served once complete. What breaks it is **post-processing**: yt-dlp's `FixupM4a`, remuxing, or tagging produce a new file. So the stream must come from the raw `.part`/download file, and post-processing must happen after the download, into a separate file.
2. **Time to first sample** is 0.1–0.3 s on top of the download's first bytes for every good layout, even at about real-time rate. Faststart M4A is the slow one: about 1.3 s at real-time rate, because the whole moov (sample tables for every frame) must arrive first. The ≤ 5 s target in SPEC §6 is therefore decided by yt-dlp and YouTube (T03c), not by the streaming layer. Two things still add delay:
   - ExoPlayer's `DefaultLoadControl` waits for `bufferForPlaybackMs` = 2.5 s of media before starting. At a download rate close to real time that is up to about 2.5 s of wall time.
   - If the worker hands over only after N bytes have been written, that wait is added too.
3. **Unknown length + unknown duration means ExoPlayer treats the stream as live.** This is the case for Ogg and fMP4 without `sidx` (`ProgressiveMediaPeriod.setSeekMap`: `isLive = !isLengthKnown && duration == TIME_UNSET`). It then:
   - shows no duration;
   - cannot seek (every seek is turned into a seek to 0);
   - does not seek inside the buffer;
   - after an I/O error, restarts the load from byte 0 (`configureRetry`).

   With a known length **or** a container duration (WebM with Cues at the front, fMP4 with `sidx`, faststart), ExoPlayer is "on demand": the track is seekable and retries **resume with `Range: bytes=<pos>-`**.
4. **Seek.** If the `SeekMap` is seekable, ExoPlayer turns a seek into a Range request for the target byte, and the server can only answer it once those bytes exist.
   - Seeks backwards, and forwards inside the buffer, are immediate.
   - A seek ahead of the download waits for the writer. Downloads are normally many times faster than real time (T03c), so this usually means a short wait, but past the read timeout it becomes `SocketTimeoutException`, then retries, then an error.
   - Unseekable streams snap every seek to 0, which is what SPEC §3 means by "no seek on the first play".
   - If the server ignores Range (`200`), `DefaultHttpDataSource` skips `position` bytes by reading them. This works, but costs bandwidth and waits for the download.
5. **SimpleCache does not cache a chunked first play.** `ProgressiveMediaPeriod` always sets `FLAG_DONT_CACHE_IF_LENGTH_UNKNOWN`, and `CacheDataSink` drops the write when the resolved length is unknown. Measured: 0 bytes cached, and the offline replay failed. That contradicts RF-12 ("every play goes through the cache") for every first play of a `yt:` track.
   - With an **exact `Content-Length`**, the whole track is cached, its length is stored, and the replay works offline.
   - Clearing the flag in a `ResolvingDataSource` above the cache also caches the track. But on a stream that ends cleanly too early, the cache would store the truncated length as the final length.
6. **Later plays with Range.**
   - A first play that was cut off (skip, network loss, app killed) leaves a partial span under its cache key. The next play reads that span from the cache and asks the server for `Range: bytes=<end-of-span>-`. The server must answer that with the **same bytes** as before.
   - The archived file is **not** the same bytes as the raw download: tags are written, M4A is fixed up, and mutagen cannot tag WebM, so T09 will remux to Ogg/Opus. A partial `yt:` cache entry completed from the archived file would be corrupt.
   - Media3 does not check ETags, so the cache key has to carry content identity.
7. **Estimated `Content-Length` is unsafe.**
   - Too large: the stream ends early, OkHttp throws, the 3 retries with Range fail, and playback errors.
   - Too small: the track is cut off, and the cache stores the wrong length for good.
   - With a known length, Ogg seeks to the end. The only safe lengths are exact or none. yt-dlp knows the exact size of YouTube DASH audio before it downloads (`filesize`, from the `clen` URL parameter).

## Failure behaviour

- Once the status line and headers are sent, the status cannot change. The only in-band signal is **how the body ends**:
  - Aborting the connection without the final chunk (chunked) or before `Content-Length` is reached is seen at once as an I/O error by OkHttp (`EOFException` / `ProtocolException`), curl (exit 18) and ffmpeg.
  - A clean end of a chunked body is **indistinguishable from the real end of the track**. The client plays a truncated song and moves on; with the cache flag cleared, it would also cache the truncated song as complete. **Never end a failed stream cleanly.**
  - In Starlette/uvicorn, raising inside the `StreamingResponse` generator closes the socket without the final chunk (checked). With a `Content-Length`, h11 also refuses to finish a short body and closes the connection.
- ExoPlayer then retries (`DefaultLoadErrorHandlingPolicy`: at least 3 retries for on-demand and 6 for "live" streams, with delays of 0/1/2… s up to 5 s):
  - with a length or duration known, it retries with Range from the last position;
  - otherwise, after the buffer runs dry, it reloads from 0.
- The retry is where the server can answer with a clean error. While the job is `failed`, the api answers the retry with an HTTP error, and ExoPlayer surfaces `ERROR_CODE_IO_BAD_HTTP_STATUS` after the retries. The best code is `404` with the OpenSubsonic error body (code 70 "not found"), or `410`/`502`. The error is visible within a few seconds of the failure. The app also polls the job status (T17) and can show "download failed" sooner.
- Third-party clients see the same truncated-body error, then the error status on retry. How each client shows it varies (see the manual protocol below).

## Recommendation

**Worker (T08) — container and format policy, with T03c**

- Prefer **Opus in WebM (itag 251)**; fall back to **AAC fMP4 (itag 140)**. Both are front-indexed as YouTube serves them.
- Download the raw stream sequentially into `/staging/<job>.part` and **never rewrite it in place**.
- Run all post-processing **after** the download is complete, into a new file: yt-dlp `FixupM4a` (or `--fixup never` plus our own step), remux to Ogg/Opus for tagging, tags, ReplayGain.
- Report to the api, through the internal worker API, as early as possible:
  - `expected_size` (yt-dlp `filesize`; `null` if only `filesize_approx` is known);
  - container and MIME type;
  - `bytes_written` progress.
- Any format whose metadata sits at the end must not be streamed while downloading: M4A with the moov at the end, WebM with Cues at the end and a SeekHead, MP3 without a header. If yt-dlp ever picks one, the api waits for the job to finish before streaming.

**api `stream`/`download` for `yt:` ids while the job runs (T16)**

- Start the response as soon as the first bytes exist (`bytes_written > 0`). Do not wait for a byte threshold; the client's buffer already plays that role.
- Set `Content-Type` from the container (`audio/webm` or `audio/mp4`). No `Content-Encoding`. `Cache-Control: no-store` (the URL carries the API key).
- **If `expected_size` is known (the normal case):**
  - answer `200` with an exact `Content-Length` and `Accept-Ranges: bytes`;
  - support Range on the in-progress file: `206` with `Content-Range: bytes a-b/<expected_size>`, headers sent at once, and the body trickled as the writer advances;
  - `bytes=0-` gets `206 bytes 0-(N-1)/N`;
  - a start beyond `expected_size` gets `416`;
  - no wait timeout on the server side. The client's read timeout governs, and the request ends if the job fails.
- **If `expected_size` is unknown:** answer `200` chunked, with no `Content-Length` and `Accept-Ranges: none`.
  - A Range request then gets `200` from byte 0 (RFC 9110 allows ignoring Range). Do **not** invent `bytes 0-*/*`: it is not valid syntax.
  - The first play is then neither cached nor seekable on our client. That is acceptable for a rare fallback.
- **Never send an estimated `Content-Length`.**
- **On job failure,** abort every open stream of that job: raise in the generator so no final chunk is sent and the connection is not closed cleanly. Answer every later request for that `yt:` id with the OpenSubsonic error (HTTP 404, code 70) until the job is retried.
- One `InFlight` entry per video id. Several listeners tail the same `.part`, and each response keeps its own file offset.
- Once the job is archived, the `yt:` id becomes an alias. New requests are served from the library file with normal Range support. Because the bytes differ (see client rules), the aliased stream should also advertise the new size. Clients must not complete an old partial cache entry with it.

**Client (T17)**

- Use the OkHttp data source and keep `ProgressiveMediaSource` with `DefaultExtractorsFactory`.
- Raise the read timeout of the stream data source to 20–30 s, so that a seek ahead of the download waits instead of failing.
- Lower `bufferForPlaybackMs` to about 1 s for first plays of `yt:` tracks.
- Seek:
  - offer it only when `player.isCurrentMediaItemSeekable` is true;
  - with the policy above that is true for WebM/fMP4 first plays, and a forward seek past the download waits;
  - when it is false (chunked fallback), disable the scrubber and lyric-tap seek, as SPEC §3 says.
- Cache key = the played id (`yt:<videoId>` or the library UUID). The app always resolves a `yt:` id to its library id before playing, once the server reports it archived (getSong / alias).
  - When a `yt:` id becomes archived, or a first play ends with an error or incomplete, remove the cache resource for that `yt:` key (`Cache.removeResource`). A raw-bytes entry must never be completed from the archived file.
  - The first library play downloads the archived file once more. That cost is accepted.
- Do not clear `FLAG_DONT_CACHE_IF_LENGTH_UNKNOWN`.

## Proposed SPEC §11 decision text

> - **Streaming while downloading** (2026-10-12, T03a):
>   - **Worker:** downloads the YouTube audio stream as is (Opus/WebM itag 251, fallback AAC fMP4 itag 140; both expected to be front-indexed per YouTube's DASH `indexRange`, **to be confirmed on real files by the T03c download run**) sequentially into `/staging` and never rewrites that file. Fix-ups, remux, tags and ReplayGain happen after the download, into a new file. It reports the exact `expected_size` (yt-dlp `filesize`) as soon as it is known.
>   - **api, `yt:` id in flight, known size:** answers `200` with an exact `Content-Length` and `Accept-Ranges: bytes`, and `206` for Range requests on the growing file (`Content-Range: bytes a-b/<size>`, bytes sent as the writer advances, `416` past the size).
>   - **api, unknown size:** answers chunked with no `Content-Length` and ignores Range (`200` from byte 0).
>   - **Never** an estimated `Content-Length`, never `bytes 0-*/*`. Formats with their index at the end (M4A moov at the end, WebM Cues at the end) are only served once complete.
>   - **Job fails mid-stream:** the api aborts the response without a terminating chunk, then answers retries with error 70 (HTTP 404).
>   - **Client:** seeks on a first play only when Media3 reports the item seekable (a forward seek waits for the download). Read timeout 20–30 s. Its cache key is the played id, and it drops any `yt:` cache entry once the track is archived or the first play ends incomplete. Reason: chunked responses are never written to Media3's `SimpleCache`, ends-of-file indexes stall progressive playback, and archived files differ byte-for-byte from the raw download.
>   - **SPEC §3 "no seek on the first play"** becomes "seek on the first play only where the container and known size allow it".

## Manual test protocol for the author (third-party clients)

Needs: the test stack (`server/compose.test.yaml`), with the fake downloader writing a front-indexed WebM/Opus and an fMP4 file **slowly** (about 20 KB/s, so a 3-minute track takes about 2 minutes). A failure switch on the fake downloader (fail at about 40 %). The phone on the same LAN or Tailscale. Tempo (Media3-based) and Substreamer; Symfonium too if available.

For each client, and for each server mode (A: exact `Content-Length` + Range; B: chunked fallback, forced with a debug setting):

1. **Connect** with an API key (or the key as password). Find a track that is not in the library (search shows it as external; Symfonium searches locally, so start it from a `yt:` id in a server-side playlist instead).
2. **First sound:** tap play and time it with a stopwatch until you hear sound. Write down the number of seconds and whether the client shows a duration.
3. **Seek forward** to about 75 % while the download is at about 30 % (watch the admin panel's queue). Write down: no reaction / snaps to 0 / waits then plays / error.
4. **Seek backward** to 10 s. Write down the result.
5. **Let it finish.** Does it play to the end without stopping, and does the next queue item start?
6. **Replay offline:** turn on airplane mode and play the same track again. Does it play from the client's cache?
7. **Failure:** with the failure switch on, play a new external track. Write down what the client shows when the download breaks (silence, skip to next, error message) and how long it takes.
8. **After archive:** once the job is done, play the track again, from search (it should now be a library id) and from the old queue entry (the `yt:` id). Both must play the whole track without glitches or a wrong duration.
9. Record the results per client and mode in `docs/compat.md` (T19). Check the server logs for the `Range` headers each client sent (logged without query strings).
