# T03c — yt-dlp today

## Question
What does the worker need to download audio from YouTube Music reliably today, without an account, from the home IP?

1. Which JavaScript runtime yt-dlp needs (EJS challenge solver), its license, size and RAM.
2. The PO-token situation without an account, and which player clients work.
3. The best format selector for original-format audio (Opus/WebM 251, AAC/M4A 140) and whether the file can be streamed while it downloads.
4. Time to first byte and download time per track, and how yt-dlp writes partial files and reports progress.
5. How yt-dlp updates itself inside a read-only container, using the `/opt/ytdlp` volume, and how that update is verified.
6. Whether GitHub Actions runner IPs get blocked.

## Findings

### 1. JavaScript runtime
- yt-dlp now solves YouTube's JS challenges (`n` and signature) with **EJS**: the external scripts in `yt-dlp-ejs`, run by an external runtime. The official zipapp and binaries **bundle** `yt-dlp-ejs` (`yt_dlp_ejs/yt/solver/*.min.js` is inside the zip), so `--remote-components` is not needed. It stays off, so yt-dlp never downloads scripts from npm or GitHub at runtime.
- Supported runtimes, in priority order: **deno** (≥ 2.3.0, the only one enabled by default, recommended upstream, runs with no file-system or network permission), **node** (≥ 22; Debian trixie has 20, so it is unusable without a third-party repository), **quickjs / QuickJS-NG** (works, but yt-dlp writes temp files for it, with a theoretical TOCTOU; it was 2.5–3× slower here), and **bun** (deprecated, has no sandbox, versions after 1.3.14 are unsupported).
- **Today the default path executes no JS at all.** The `visionos` client returns direct https audio URLs without a challenge. JS is needed only when we fall back to a web client such as `web_embedded`. In that case Deno adds ~2 s and a **transient ~326 MB** process. QuickJS adds 7–11 s, which by itself breaks the 5 s first-sound target (SPEC §6).
- Without any runtime, extraction still works today, but yt-dlp warns that runtime-less YouTube extraction is deprecated. We should not depend on that.
- Licenses: Deno **MIT**, bundled V8 BSD-3-Clause; QuickJS / QuickJS-NG MIT; yt-dlp **Unlicense**; yt-dlp-ejs Unlicense AND MIT AND ISC. All are free software and GPL-3.0-or-later compatible.
- Size: Deno 2.9.7 is a single 96 MB binary (41.6 MB zip, needs only glibc and libgcc, which `python:3.13-slim` has). QuickJS is about 1–2.5 MB.
- Deno needs no writable home: a run with a read-only `$HOME` still solved the challenge, because yt-dlp calls `deno run --no-remote --no-npm --cached-only --no-config --no-code-cache -`.
- **Recommendation: Deno**, pinned and verified in the Dockerfile. It is upstream's recommended and best-sandboxed runtime, and the only one fast enough for the fallback path.

### 3. Format selection, original container, streaming while downloading
- **Opus in WebM, itag 251** (~130–140 kb/s, 48 kHz) is the best audio YouTube offers without an account. **AAC-LC in M4A, itag 140** (~128 kb/s, 44.1 kHz) is the fallback. Formats 249/250 (low-bitrate Opus) and 139 (HE-AAC 49 kb/s) are worse. 233/234 are HLS (m3u8, fragment-based) and should be avoided for streaming while downloading.
- Selector, by exact itag first so that variants such as `251-drc` (stable volume) and HLS are never picked:
  ```
  251/bestaudio[acodec=opus][protocol=https]/140/bestaudio[ext=m4a][protocol=https]
  ```
  With no video selected there is no merge, so ffmpeg is not called during download.
- **Keeping the original container.** `-f` alone never transcodes. However, yt-dlp's default fixups run `FFmpegFixupM4aPP` on `m4a_dash` (format 140), which remuxes the file to plain MP4 with `-f mp4` and **without** `+faststart`. That puts `moov` at the end **and rewrites the file in place** while the api might be reading it. Pass `--fixup never`. T09 can then remux an M4A once, at archive time, with `-c copy -movflags +faststart` (a remux, not a transcode). WebM gets no fixup.
- **Streaming while downloading** (for T03a): format 251 is downloaded as **one sequential https GET**. yt-dlp uses `Range` chunks of 10 MiB (`http_chunk_size`), and every track is under 10 MiB. Bytes are appended to the file in order.
  - WebM/Opus is playable from the first cluster without an index.
  - YouTube's DASH M4A is fragmented MP4 (`ftyp`/`moov`/`sidx` followed by `moof`/`mdat`). It is also playable while growing, but only if the fixup is disabled.
  - **WebM/Opus is the primary format** for streaming while downloading. A real download should confirm the byte layout with `ffprobe`, which is part of the pending measurement.
- **Write granularity.** yt-dlp reads with an adaptive block size that starts at 1 KiB and grows up to 4 MiB, so on a fast link the file can grow in multi-MB jumps. `--buffer-size 64K --no-resize-buffer` keeps growth smooth for the streaming reader at negligible cost.

### 4. Partial files, progress, timing
- **`.part` (default).** yt-dlp writes `<name>.<ext>.part`. On success it renames the file to `<name>.<ext>` with `os.replace`, so the final name exists only when the download is complete. The rename keeps the inode, so an api reader that opened the `.part` file keeps reading the same data after the rename. **Recommended:** the api streams from the path the worker reports in progress (`tmpfilename`) and treats the job state, not the file name, as the end-of-stream signal.
- **`--no-part` is a trap for retries.** If a partial file exists under the final name, the next attempt considers it "already downloaded" unless `--force-overwrites` is passed, and that flag truncates the file under any reader. Do not use it.
- **Resume.** With `.part`, a retry continues from the current size with an HTTP `Range` (`--continue`, the default) and appends. A reader still sees one monotonically growing file. The URL is re-extracted on each attempt.
- **`-o -` (stdout)** works, but the worker would then copy the pipe itself and lose resume. It brings no advantage over `.part`.
- **Progress.** Use `--progress --newline --progress-delta 0.5 --progress-template 'download:UTP %(progress.{status,downloaded_bytes,total_bytes,total_bytes_estimate,speed,eta,tmpfilename,filename})j'`. This prints one JSON object per line after the fixed prefix `UTP `, and keys with no value are omitted. The template was verified offline with yt-dlp's own `evaluate_outtmpl`.
- **Result line.** Use `--print 'after_move:UTF %(.{id,format_id,ext,acodec,abr,asr,filesize,duration,filepath})j'` for the final file and format. `--print` implies `--quiet`, so `--progress` must be passed explicitly. Any other stdout or stderr line is a log line or a `WARNING:`/`ERROR:` line, used for classification.
- **Timing.** Extraction takes 1.5–1.8 s on the default path; googlevideo answered in 30–80 ms. That leaves about 3 s of the 5 s first-sound budget for the api and ExoPlayer (T03a). The fallback path (`web_embedded` with Deno) takes about 3.8 s before the first byte and would be tight. Real download timings are pending (see *Limitation*).

### 5. Self-update inside a read-only container
- The **zipapp** (`yt-dlp` release asset, 3 MB, Python ≥ 3.10) is the right unit. It is one file, it bundles `yt-dlp-ejs`, and it runs under the image's Python with no site-packages (`python -I -S` worked). It falls back to `urllib` and the system CA store; `requests`, `certifi`, `brotli` and `websockets` are optional and not needed for YouTube.
- **Verification.** Each release publishes `SHA2-256SUMS` and `SHA2-256SUMS.sig`, signed with the yt-dlp key `AC0C BBE6 848D 6A87 3464 AF4E 57CF 6593 3B5A 7581` ("Simon Sawicki (yt-dlp signing key)"). The nightly repository `yt-dlp/yt-dlp-nightly-builds` publishes the same three files. In this spike, `gpg --verify SHA2-256SUMS.sig SHA2-256SUMS` reported a good signature and `sha256sum -c` matched for 2026.08.19.
- **yt-dlp's own `-U` / `--update-to`** works on a zipapp in a writable directory (tested 2026.07.04 → 2026.08.19). It checks the SHA-256 from `SHA2-256SUMS`, but only over TLS: it does **not** verify the GPG signature. It also overwrites the zip **in place**, so a yt-dlp process that is importing from that zip at the same moment can crash. It is acceptable as a manual fallback, but not as the worker's mechanism.
- **Recommended updater** (worker, T08; httpx and argument lists only):
  1. Get the latest tag of `yt-dlp/yt-dlp` (stable, default) or `yt-dlp/yt-dlp-nightly-builds` (`UT_YTDLP_CHANNEL=nightly`) from the GitHub releases API. Validate the tag against `^\d{4}\.\d{2}\.\d{2}(\.\d+)?$`, and stop if it equals the current one.
  2. Download `yt-dlp`, `SHA2-256SUMS` and `SHA2-256SUMS.sig` into `/opt/ytdlp/tmp/<tag>/`. Use a size cap and a timeout.
  3. Run `["gpgv", "--status-fd", "1", "--keyring", "/usr/local/share/ultimatetunes/yt-dlp-keyring.gpg", "SHA2-256SUMS.sig", "SHA2-256SUMS"]`. It must exit 0 **and** print `VALIDSIG` with the pinned fingerprint. The keyring is baked into the image and is read-only.
  4. Check that the SHA-256 of `yt-dlp` equals the `SHA2-256SUMS` line ending in ` yt-dlp`.
  5. Smoke test: `[python, "-I", "-S", ".../yt-dlp", "--version"]` must print the tag. Optionally run the canary with the new version too.
  6. `os.rename` the directory to `/opt/ytdlp/releases/<tag>/`, then atomically swap the `/opt/ytdlp/current` symlink (create `current.tmp`, then `os.replace`). Keep the previous two releases for rollback.

  Release directories are immutable, and each job resolves `current` when it starts, so an update never touches a running download. The updater runs at worker start, every `UT_YTDLP_UPDATE_INTERVAL` (default 24 h), from the admin "update now" button, and after a canary failure. If the volume is empty, the worker first copies the **seed** zipapp from the image.
- `pip --target /opt/ytdlp/...` would also work, but it pulls several wheels whose hashes can only be checked against PyPI over TLS, and it gains nothing over the signed single file.
- New outbound hosts for the update: `api.github.com`, `github.com` and `release-assets.githubusercontent.com` / `objects.githubusercontent.com`. The CLAUDE.md list of hosts the server contacts must name them ("yt-dlp updates from GitHub releases").

### 6. GitHub Actions runner IPs
This was not run on GitHub; the conclusion comes from upstream issues.
- YouTube walls datacenter ASNs with *"Sign in to confirm you're not a bot"*. yt-dlp maintainers answer it with "don't use a datacenter IP" (yt-dlp#12475, 2025-02). They repeat it in 2026-02: "YT does not trust your IP address enough to allow anonymous access" (bashonly, same issue). The tracking issue is yt-dlp#10128, and reports from cloud/VPS users say every client returns `LOGIN_REQUIRED`.
- Runners on Azure IPs fall in this class. Results would flip between green and red for reasons unrelated to yt-dlp. A canary there is **noise, not signal**, and the only workaround (cookies from an account in CI) is out of scope and against the privacy rules.

## Recommended `Downloader` design (T08)
- Use the interface `Downloader.download(video_id, staging_dir, on_progress) -> DownloadResult`. The implementation is `YtDlpDownloader`, a **subprocess** (`asyncio.create_subprocess_exec`, never `shell=True`), and never `import yt_dlp`. Running it as a subprocess means the updated zipapp is used, a crash or leak is isolated, and the process can be killed on lease loss or SIGTERM.
- Validate `video_id` against `^[A-Za-z0-9_-]{11}$` **before** building the arguments. Ids can start with `-`, so the URL always comes after `--`.
- Argument list:
  ```python
  [
      sys.executable, "-I", "-S", str(ytdlp_current / "yt-dlp"),
      "--ignore-config", "--no-plugin-dirs", "--no-cache-dir",
      "--no-playlist", "--no-mtime", "--fixup", "never", "--no-remote-components",
      "--no-js-runtimes", "--js-runtimes", f"deno:{DENO_PATH}",
      "--extractor-args", f"youtube:player_client={clients}",   # from UT_YTDLP_PLAYER_CLIENTS
      "--format", "251/bestaudio[acodec=opus][protocol=https]/140/bestaudio[ext=m4a][protocol=https]",
      "--retries", "3", "--socket-timeout", "20", "--throttled-rate", "100K",
      "--buffer-size", "64K", "--no-resize-buffer",
      "--progress", "--newline", "--progress-delta", "0.5",
      "--progress-template", "download:UTP %(progress.{status,downloaded_bytes,total_bytes,total_bytes_estimate,speed,eta,tmpfilename,filename})j",
      "--print", "after_move:UTF %(.{id,format_id,ext,acodec,abr,asr,filesize,duration,filepath})j",
      "--paths", f"home:{staging_dir}", "--paths", f"temp:{staging_dir}",
      "--output", f"{video_id}.%(ext)s",
      "--", f"https://www.youtube.com/watch?v={video_id}",
  ]
  ```
  `staging_dir` comes from `StagingStore` (`/staging/<job-id>/`). The environment is minimal: `HOME`, `PATH`, `TMPDIR`, `DENO_NO_UPDATE_CHECK=1`, and never secrets.
- **Client ladder.** First attempt with `default`. On `Requested format is not available`, or a PO-token or SABR warning, retry once with `web_embedded`, which needs Deno. Both ladders are settings.
- **Parsing.** Lines starting with `UTP ` carry JSON progress, which goes to the internal API, throttled. The `UTF ` line carries the final result. `ERROR:` lines are classified as below. Everything else is logged at debug level, after redaction (googlevideo URLs carry the client IP in query parameters, so never log full URLs). The first `tmpfilename` is reported to the api as the streamable path.
- **Error classes.**

| Class | Signals | Action |
|---|---|---|
| Transient | network or timeout errors, HTTP 5xx, `HTTP Error 403` during download (expired URL), `ContentTooShortError`, `The page needs to be reloaded` | Retry with backoff (max 3, RF-04); `.part` resumes |
| Extractor outdated | `Requested format is not available` after the client ladder, `n challenge solving failed`, `Signature extraction failed`, `Unable to extract`, `Some formats may be missing` | Trigger an update, then retry once with the new version; if it still fails, fail the job and raise a canary alert |
| Blocked (global) | `Sign in to confirm you're not a bot`, `HTTP Error 429` | Do not burn per-job retries: pause the queue (circuit breaker, e.g. 30 min, doubling), notify the admin (RF-13) |
| Permanent (this video) | `Video unavailable`, `Private video`, `This video has been removed`, geo-restriction (`GeoRestrictedError`, "not available in your country"), `Sign in to confirm your age`, members-only, live or upcoming | Fail without retry; the track is marked failed (RF-05: clean error to the listener) |
| Local | `ENOSPC`, permission errors on `/staging` | Fail; readiness and admin alert |

  Exit codes: 0 = ok, 1 = error (classify by the `ERROR:` text), 2 = usage error (a bug on our side, never retried).

## Proposed Dockerfile changes (T00/T08)
The base image stays `python:3.13-slim` (Debian 13 "trixie").

```dockerfile
# --- verified tools stage (not shipped) ---
FROM python:3.13-slim AS tools
ARG TARGETARCH
ARG DENO_VERSION=2.9.7
ARG DENO_SHA256_amd64=c6527f24f4b16031d3ae4fa9f658d5f11534c8d84ce7dc8502420280919c3490
ARG DENO_SHA256_arm64=c832298b1ad4422481334855f6003e0f54145762c5a134f20a489511d2f65bbf
ARG YTDLP_SEED_VERSION=2026.08.19
ARG YTDLP_SEED_SHA256=1fa6733c37ea6fb51c99ad8fe785e7b7e5f3246c9b980230329d4fb72ed8d4d6
# yt-dlp release key fingerprint (public), in gpg's grouped form; spaces are stripped below.
ARG YTDLP_KEY_FPR="AC0C BBE6 848D 6A87 3464  AF4E 57CF 6593 3B5A 7581"
RUN apt-get update && apt-get install -y --no-install-recommends gnupg && rm -rf /var/lib/apt/lists/*
COPY server/docker/yt-dlp-public.key /tmp/yt-dlp-public.key   # committed copy of upstream public.key
COPY server/docker/fetch-verified.py /tmp/fetch-verified.py    # urllib download + sha256 check (no curl)
RUN set -eu; \
    case "$TARGETARCH" in amd64) a=x86_64; s="$DENO_SHA256_amd64";; arm64) a=aarch64; s="$DENO_SHA256_arm64";; *) exit 1;; esac; \
    python -I /tmp/fetch-verified.py "https://github.com/denoland/deno/releases/download/v${DENO_VERSION}/deno-${a}-unknown-linux-gnu.zip" "$s" /tmp/deno.zip; \
    python -I -m zipfile -e /tmp/deno.zip /out/bin/ && chmod 0755 /out/bin/deno; \
    gpg --batch --no-default-keyring --keyring /out/share/yt-dlp-keyring.gpg --import /tmp/yt-dlp-public.key; \
    fpr=$(printf '%s' "$YTDLP_KEY_FPR" | tr -d ' '); test "${#fpr}" -eq 40; \
    gpg --batch --no-default-keyring --keyring /out/share/yt-dlp-keyring.gpg --with-colons --fingerprint | grep -q "^fpr:::::::::${fpr}:"; \
    python -I /tmp/fetch-verified.py "https://github.com/yt-dlp/yt-dlp/releases/download/${YTDLP_SEED_VERSION}/yt-dlp" "$YTDLP_SEED_SHA256" /out/share/yt-dlp-seed/yt-dlp

# --- runtime ---
FROM python:3.13-slim
RUN apt-get update \
 && apt-get install -y --no-install-recommends ffmpeg gpgv ca-certificates \
 && rm -rf /var/lib/apt/lists/*
COPY --from=tools /out/bin/deno /usr/local/bin/deno
COPY --from=tools /out/share/ /usr/local/share/ultimatetunes/
ENV UT_DENO_PATH=/usr/local/bin/deno \
    UT_YTDLP_DIR=/opt/ytdlp \
    UT_YTDLP_CHANNEL=stable \
    UT_YTDLP_UPDATE_INTERVAL=24h \
    UT_YTDLP_PLAYER_CLIENTS=default \
    UT_YTDLP_FALLBACK_CLIENTS=web_embedded \
    DENO_NO_UPDATE_CHECK=1 \
    HOME=/tmp
VOLUME ["/opt/ytdlp"]
# ... app install, non-root USER, read-only rootfs as in T00
```

- **apt packages:** `ffmpeg`, needed by T09 for ReplayGain and the M4A faststart remux (Debian 7.1.5, +469 MB / 208 packages with `--no-install-recommends`; large but security-maintained and visible to Trivy); `gpgv` (+2.8 MB); and `ca-certificates`, already present.
- **Deno:** pinned version plus per-architecture SHA-256 in `ARG`s, downloaded in a build stage (no curl, no `| sh`). It is a 96 MB binary.
- **yt-dlp:** a seed zipapp pinned by SHA-256 lives in the read-only image. The live copy is in the volume.
- `yt-dlp` should **not** be a runtime dependency in `pyproject.toml`/`uv.lock`; at most a dev dependency if tests need its types. Otherwise there are two copies and the wrong one may be imported.
- **`/opt/ytdlp` volume layout** (worker only, owned by the worker uid):
  ```
  /opt/ytdlp/
    current -> releases/2026.08.19      # symlink, swapped atomically
    releases/<tag>/yt-dlp               # immutable once verified
    tmp/                                # downloads in progress (cleaned at start)
    state.json                          # current tag, last check, last canary result
  ```
- **Writable paths for the worker:** `/opt/ytdlp`, `/staging`, `/music`, and a `/tmp` tmpfs (yt-dlp has nothing to cache: with EJS, `--cache-dir` stayed empty, so it uses `--no-cache-dir`).
- **Memory:** the worker idles with no yt-dlp process. During a job, yt-dlp uses ~65 MB, and a Deno solve briefly adds ~330 MB. Set the worker's `mem_limit` to at least 512 MB; the idle budget in SPEC §6 is unaffected.

## Canary recommendation
- Run the scheduled canary **on the server** (the worker's `canary` command, daily with random jitter, result in the admin panel and RF-13 notifications).
  1. `--simulate` extraction of `Yy-NyPTRYU8` ("Exit the Premises", Kevin MacLeod, CC BY) with the production arguments, asserting format 251 and a `license` that contains "Creative Commons".
  2. A real download of that one track into `/staging/canary/`, deleted afterwards, asserting the WebM/Opus header and a size within ±5 % of the size reported at extraction.
  3. Record the yt-dlp version, the client used, the extraction time and the time to first byte.
- On failure, run the updater and the canary again. If it still fails, alert the admin.

## Proposed SPEC §11 decision (2026-10-12, T03c)
> **yt-dlp setup (2026-10-12, T03c).** The worker runs yt-dlp as a subprocess (argument list, never `import yt_dlp`), from the official signed **zipapp** kept in the `/opt/ytdlp` volume. The image carries a pinned seed copy. The worker updates it itself: GitHub release, then `gpgv` against the pinned yt-dlp key, then SHA-256, then a smoke test, then an atomic symlink swap. Stable channel by default; nightly is a setting. The JS runtime is **Deno** (MIT), pinned by version and SHA-256 in the Dockerfile, with no remote components. The format policy is original audio only: `251/bestaudio[acodec=opus][protocol=https]/140/bestaudio[ext=m4a][protocol=https]` with `--fixup never` (Opus/WebM preferred; M4A only as a fallback, remuxed with faststart at archive time; never transcoded). Player clients come from settings (today `default` → `visionos`, falling back to `web_embedded`). No PO-token provider and no cookies in v1. Partial downloads use yt-dlp's `.part` file, which the api streams. The scheduled canary runs on the server, not on GitHub runners (datacenter IPs get the bot wall); the GitHub job stays manual. New outbound host for the server: GitHub releases, for yt-dlp updates only.
