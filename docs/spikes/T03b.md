# T03b — YouTube Music from the server

## Question
Does `ytmusicapi` work today, **without an account**, from the home IP, for everything RF-03 (search), RF-06 (radio) and RF-08 (playlist import) need? What does it return, how fast is it, when does it throttle, and how should `MusicCatalog` wrap it (ids, caching, rate limiting, retries, hosts)?

**Short answer: yes.** Every capability we need works anonymously. Over 124 HTTP requests in about 5 minutes (including a burst of 25 searches with no pause) there were no throttling or blocking signals: every response was HTTP 200. Search is fast enough for the `search3` target (p95 ≈ 0.5–0.75 s per call against a 2 s budget). There are two traps: `language="es"` breaks filtered search, and invalid ids raise a bare `KeyError`.

## Setup
- Date: 2026-10-12. Home connection (Spain), no cookies, no OAuth, no proxy.
- `ytmusicapi` **1.12.3** (MIT) on Python 3.13.15. It pulls in **`requests` 2.34.2** (Apache-2.0) plus `urllib3` (MIT), `charset-normalizer` (MIT), `idna` (BSD-3), `certifi` (MPL-2.0). All are GPL-3.0-compatible. **ytmusicapi is synchronous and built on `requests`, not `httpx`.** It accepts a custom `requests.Session`, which we used to log every request and set a 15 s timeout (the library default is 30 s).
- One `YTMusic()` instance per locale, `language="en"`, `location=""` unless stated otherwise. Calls were paced 1–2.5 s apart, except the burst test.
- Throwaway code in `spikes/t03b/` (git-ignored). Docs from Context7 (`/websites/ytmusicapi_readthedocs_io`).
- Budget used: **124 requests** (92 `search`, 15 `browse`, 5 `next`, 2 `player`, 10 `GET /`), all to `music.youtube.com`, all HTTP 200. Peak RSS of the spike process: **40–56 MB** (interpreter + ytmusicapi + requests + parsed responses held in memory).

## Findings per capability

### Search (RF-03)
- **Quality is very good** for typical queries. On 44 song queries (24 in English, 20 in Spanish, artist + title), the right song by the right artist was the **top result in all 44**. Accent-free and misspelt queries were corrected server-side: `rosalia malamente`, `heroes del silenco …` and `beatls yesterday` all came back right. `ignore_spelling=True` still put the right song first.
- **Album choice is the weak point.** The top song hit is sometimes on a compilation or deluxe edition: Billie Jean → *HIStory*, Let It Be → *1*, HUMBLE. → *DAMN. COLLECTORS EDITION.*, Shake It Off → *1989 (Deluxe)*. MusicBrainz tagging (T09) has to normalise this.
- Song fields (`filter="songs"`): `videoId`, `title`, `artists[{name,id}]`, `album{name,id}` (present in 480/480 results), `duration` + `duration_seconds`, `isExplicit`, `videoType` (always `MUSIC_VIDEO_TYPE_ATV` with this filter), `views`, `thumbnails` (60 and 120 px), and `year` (**always null** in song results). `artists[].id` is null for "Various Artists" and some small uploaders (24/480).
- Album fields (`filter="albums"`): `browseId` (`MPREb_…`), `playlistId` (`OLAK5uy_…`), `title`, `type` (Album/Single/EP), `year`, `artists`, `isExplicit`, `thumbnails`.
- Artist fields (`filter="artists"`): `browseId` (= `channelId`, `UC…`), `artist` (name), `radioId`, `shuffleId`, `thumbnails`. Generic names return look-alikes after the real artist ("Calm Down Oasis").
- `limit` is a minimum, not a maximum: `limit=10` returned 20, one page. Trim on our side.
- **The unfiltered `search()` is unusable as the main search.** Most items come back with `category: null`, and the list mixes in videos, podcast episodes and community playlists. Use three filtered calls (songs, albums, artists) in parallel instead.
- **`language="es"` breaks filtered search**: `filter="songs"` returns `[]` silently, while unfiltered search returns localised categories ("Más de YouTube"). `language="en"` with `location="ES"` works, but changes the ranking (it picked the "Bonus Tracks Edition" album). Recommendation: always `language="en"`; make `location` an optional env setting (default empty, which lets YouTube use the IP).

### Album and artist pages
- `get_album(MPREb_…)`: `title`, `type`, `year`, `trackCount`, `duration_seconds`, `artists` (album artists), `audioPlaylistId`, `description` (Wikipedia text with en.wikipedia.org and creativecommons.org links, **not to be fetched**), `other_versions`, `thumbnails` up to 544 px. Tracks carry `trackNumber`, `videoId`, `duration_seconds`, `isExplicit`, `isAvailable` and `videoType`. All tracks were available in the 3 albums tested.
- **The same song has several `videoId`s.** Search returned Wonderwall as `hpSrLjc5SMs` (ATV, album `MPREb_PITqkpE6ExP`, a remaster edition). The 1995 album page `MPREb_IInSY5QXXrW` lists it as `6hzrDeceEKc` (OMV, the music-video audio). Several `yt:` ids must therefore be able to point to one library track (aliases), and the dedup key cannot be the videoId alone.
- `get_artist(UC…)`: `name`, `channelId`, `description`, `monthlyListeners`, `subscribers`, `radioId`, `shuffleId`, `thumbnails`, plus sections `songs` (5 + a `browseId` of the full "songs" playlist), `albums` (10 + `params` for the full list via `get_artist_albums`), `singles`, `videos` and `related`. Some artists also have `episodes` and `podcasts`.

### Watch playlist / radio (RF-06)
- `get_watch_playlist(videoId=…, radio=True)` returns **50 tracks in one request**, whatever the `limit` (25 here, which acts as a minimum). It returns `playlistId: RDAMVM<videoId>`, `lyrics: MPLYt_…` and `related: MPTRt_…`. Track 0 is the seed itself, with full metadata.
- Tracks carry `videoId`, `title`, `length` (string), `artists`, `album{name,id}`, `year` (**present here**), `videoType`, `thumbnail`. Mostly ATV; one UGC upload without an album appeared in the ROSALÍA radio. Relevance was good: Oasis → Oasis, Radiohead, The Killers…; Vetusta Morla → Vetusta Morla, Viva Suecia, Jarabe de Palo…
- `radio=False` and `radio=True` gave the same `RDAMVM` list for a song seed. The docs say the radio "changes each time", so cache it per seed for the queue's lifetime, not across sessions.
- **Watch playlist track 0 is the cheapest full-metadata lookup for a bare `yt:<videoId>`**: one request gives album, year and artists ids. `get_song` does not include the album.

### Playlists (RF-08)
- `get_playlist` works anonymously for: YT Music featured playlists (`RDCLAK5uy_…`, 99 tracks in 1 request), plain YouTube / community playlists (`PL…`, with or without the `VL` prefix) and album playlists (`OLAK5uy_…`, from search).
- Header fields: `id`, `title`, `author{name,id}`, `privacy`, `trackCount`, `duration_seconds`, `description`, `year`, `thumbnails`.
- **Deleted or private videos:** a plain YouTube playlist reporting `trackCount: 30` returned 21 entries, 9 of them with `videoId: null`, `isAvailable: false`, `videoType: null`. The other 9 were silently omitted. The import report must count both kinds.
- Playlist entries are mostly OMV or UGC **without `album`** (89/99 in "90s Rock"; 12/15 and 21/21 in user playlists). Import therefore needs a **matching step**: a `search(filter="songs")` on "artist title" for each entry, keeping the ATV hit whose duration is within ±3 s. Without that, the import would archive music-video audio. A 50-track import costs about 51 requests, which is fine as a rate-limited job.
- URL handling (not a library feature): accept `music.youtube.com`, `www.youtube.com`, `youtube.com`, `m.youtube.com` and `youtu.be`, and take only the `list` query parameter, validated as `^(PL|OLAK5uy_|RDCLAK5uy_)[A-Za-z0-9_-]{10,}$` (also strip a leading `VL`). Reject `RD…` auto-mixes other than `RDCLAK5uy_`: they are per-user dynamic lists (not tested; they would go through `get_watch_playlist(playlistId=…)`).

### `get_song` and lyrics
- `get_song` returns `videoDetails` (`title`, `author`, `channelId`, `lengthSeconds`, `musicVideoType`), `microformat` (`publishDate`/`uploadDate`, which is the *upload* date, not the release date; `tags`; `availableCountries`), `playabilityStatus` and `streamingData`. It is **not useful for the catalog**: no album, and the streaming URLs must not be used (downloads go through yt-dlp, T03c). It is at most a cheap playability pre-check, and yt-dlp already does that. Not needed in v1.
- `get_lyrics(MPLYt…, timestamps=True)` works anonymously and returns timed lines (source: LyricFind). This is licensed third-party content; **keep LRCLIB as the only lyrics source** (RF-07). No change.

### Stable ids
| Our id | Source | Format | Notes |
|---|---|---|---|
| `yt:<videoId>` | `videoId` | `^[A-Za-z0-9_-]{11}$` | Stable per upload. One recording has several (ATV / OMV / editions), so library aliases are many-to-one. Prefer **ATV** ids (audio-only, no video intro or outro). |
| `ytalbum:<browseId>` | album `browseId` | `^MPREb_[A-Za-z0-9_-]+$` | Store `audioPlaylistId` (`OLAK5uy_…`) next to it: it is the album's playlist id, also readable with `get_playlist`, and our fallback if a `MPREb_` id stops resolving (not observed). |
| `ytartist:<channelId>` | artist `browseId`/`id` | `^UC[A-Za-z0-9_-]{22}$` | Can be null (Various Artists, uploaders). In that case keep the plain name and no id. |

### Metadata gaps vs what MusicBrainz tagging needs
Missing everywhere: **ISRC**, MusicBrainz ids, disc number, full release date (only the year), label, genre, composer. Missing in search song results: track number, year and album artist (all on the album page; year also in watch playlists). Available for an MB query: artist(s), title, album, duration in seconds and, from the album page, track number, track count, year and type. Recommended MB recording search: `artist + recording + release + dur:±3 s`, then year and track count to choose the release. Without ISRC there is no exact lookup, so `needs_review` stays important.

## Failure modes and errors seen
| Situation | What happens | Map to |
|---|---|---|
| Invalid / unknown `videoId` in `get_watch_playlist` | `YTMusicServerError: No content returned by the server` (HTTP 200) | `CatalogNotFound` |
| Invalid / unknown album or playlist id | **bare `KeyError`** from the parser (HTTP 200) | `CatalogNotFound` if the id failed our format check, otherwise `CatalogParseError` (could be a layout change → canary) |
| `language="es"` + `filter="songs"` | `[]`, no error | avoid: always `language="en"` |
| Unfiltered `search()` | items with `category: null`, mixed content types | do not use |
| Unavailable playlist entries | `videoId: null`, `isAvailable: false`, or silently missing | report as "unavailable" in the import |
| HTTP ≥ 400 (not seen) | `YTMusicServerError("Server returned HTTP …")` | 429/403 → `CatalogThrottled`; 5xx → `CatalogUnavailable` |
| Network / timeout (not seen) | `requests.exceptions.*` (default timeout 30 s) | `CatalogUnavailable` |
| Gated dialog (not seen) | `YTMusicGatedError` (subclass of `YTMusicServerError`) | `CatalogThrottled` + admin alert |

## Recommendations for `MusicCatalog` (T06/T07/T11)
**Interface** (async, typed, returns our own frozen dataclasses rather than ytmusicapi dicts):
```python
class MusicCatalog(Protocol):
    async def search_songs(self, q: str, limit: int) -> list[CatalogTrack]: ...
    async def search_albums(self, q: str, limit: int) -> list[CatalogAlbumRef]: ...
    async def search_artists(self, q: str, limit: int) -> list[CatalogArtistRef]: ...
    async def album(self, browse_id: str) -> CatalogAlbum: ...          # tracks with trackNumber
    async def artist(self, channel_id: str) -> CatalogArtist: ...       # top songs, albums
    async def track(self, video_id: str) -> CatalogTrack: ...           # = radio(...)[0]
    async def radio(self, video_id: str, limit: int) -> list[CatalogTrack]: ...
    async def playlist(self, playlist_id: str) -> CatalogPlaylist: ...  # incl. unavailable count
# CatalogTrack(video_id, title, artists: tuple[ArtistRef(name, channel_id | None)], album: AlbumRef(name, browse_id) | None,
#              duration_s, explicit, video_type: ATV|OMV|UGC|None, year: int | None, thumbnail: ThumbRef | None)
# Errors: CatalogNotFound, CatalogThrottled, CatalogUnavailable, CatalogParseError (TunesError subclasses)
```
- Implementation: **one** shared `YTMusic(language="en", location=settings.ytm_location, requests_session=…)` per process, warmed at startup (visitor id). Calls run through `anyio.to_thread.run_sync` behind a small capacity limiter (3–4 threads) because the library is synchronous. Validate every id against the regexes before calling.
- `search3` = the three filtered searches **in parallel** (≈ max of three ≈ 0.5–0.8 s), merged with the library results. If the catalog fails or takes longer than 1.5 s, return library-only results (no error to the client).
- Thumbnails: pick the largest entry. For `*.googleusercontent.com` / `yt3.ggpht.com` URLs, rewrite the size suffix (`=w60-h60-…` → `=w544-h544-…`, `=s192` → `=s544`) instead of storing several sizes. Ignore the `www.gstatic.com/…/artist_avatar@1200.png` placeholder.

**Caching** (`TtlCache` with a SQLite implementation, so nothing large stays in RAM). Store **normalised compact records**, not raw ytmusicapi dicts: a parsed 20-song page is ≈ 20 KB and a 50-track watch playlist ≈ 85 KB including tokens we do not need.

| Key | TTL | Why |
|---|---|---|
| `search:{kind}:{normalised q}` | 24 h | results barely move; saves the most requests |
| `album:{browseId}` | 7 d | stable |
| `artist:{channelId}` | 24 h | new releases |
| `track:{videoId}` | 30 d | stable; fed for free by every search, album, radio and playlist result |
| `radio:{videoId}` | 1 h | keeps a queue stable within a listening session |
| `playlist:{id}` | 10 min | imports want fresh contents |
| negative (`CatalogNotFound`) | 1 h | avoid hammering bad ids |

Purge expired rows periodically. Put the cache in its own SQLite file under `/data` so it can be deleted freely. Deduplicate concurrent identical calls with `InFlight` (single flight per cache key).

**Rate limiting and retries**
- A global `RateLimiter` for `music.youtube.com`: a token bucket at **2 req/s sustained, burst 6** (one `search3` = 3 requests). This is below the 2.5 req/s burst that worked here. Imports and the canary use the same bucket at a lower priority than interactive calls.
- Per-request timeout **5 s** (pass our own `Session`; the library default of 30 s is too long).
- Retry **once** on connection errors, timeouts and 5xx, with a jittered 0.5–1.5 s delay. **No retry** on 429/403/`YTMusicGatedError`: open a **circuit breaker** (5 min, doubling up to 1 h), serve cache and library only, log and notify the admin. `CatalogParseError` is never retried; it counts towards the canary alert, because it usually means a ytmusicapi upgrade is needed (Dependabot).
- Extend the nightly canary (T19) with 1 search + 1 radio + 1 playlist read, so that layout changes are caught early.

## Hosts the server contacts (catalog side)
- **`music.youtube.com`**: the only host ytmusicapi contacts anonymously (`GET /` once per instance for the visitor id, then `POST /youtubei/v1/{search,browse,next,player}`). The OAuth hosts (`oauth2.googleapis.com`, `www.youtube.com/o/oauth2`) are never used without an account.
- **Thumbnail / cover hosts** seen in responses (allowlist for proxying cover art of external items; https only, exact host match):
  - `yt3.googleusercontent.com`: album and song art (square)
  - `lh3.googleusercontent.com`: artist banners and some avatars
  - `yt3.ggpht.com`: channel and playlist avatars
  - `i.ytimg.com`: video thumbnails (`/vi/<id>/hqdefault.jpg`, `hq720`, `sddefault`, `maxresdefault`, 16:9) and playlist covers (`/pl_c/…`)
  - `www.gstatic.com`: placeholder artist avatar only. Do not fetch it; use our own placeholder.

  Log and drop any other host instead of fetching it. Text links in descriptions (en.wikipedia.org, creativecommons.org) are never fetched.

## Proposed SPEC §11 decision text
> **YouTube Music catalog (2026-10-12, T03b):** `ytmusicapi` (1.12.3; pulls in `requests`, Apache-2.0) is used anonymously from the server for search, album/artist pages, radio (`get_watch_playlist`) and playlist reads. Measured from the home IP: search p50 ≈ 0.4 s, p95 ≈ 0.5–0.75 s; no throttling in 124 requests including a 2.5 req/s burst. `MusicCatalog` wraps it with: `language="en"` always (`"es"` breaks filtered search), optional location from env; one shared instance driven through a thread pool; three filtered searches in parallel for `search3`, library-only fallback after 1.5 s; a global rate limit of 2 req/s (burst 6); 5 s timeout, one retry on network/5xx errors, and a circuit breaker (5 min → 1 h) with an admin alert on 429/403/gated responses; and a SQLite TTL cache of normalised records (search 24 h, album 7 d, artist 24 h, track 30 d, radio 1 h, playlist 10 min, not-found 1 h). Several videoIds may alias one library track; ATV ids are preferred, and playlist entries without an album are re-matched through song search (duration ±3 s). `get_song` and YT Music lyrics are not used (lyrics stay on LRCLIB). The server contacts `music.youtube.com`; cover proxying is limited to `yt3.googleusercontent.com`, `lh3.googleusercontent.com`, `yt3.ggpht.com` and `i.ytimg.com`.
