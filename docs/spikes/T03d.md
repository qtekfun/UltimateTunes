# T03d — Spotify playlists

*Spike run 2026-10-12. Research only: no app registered, no credentials used, no account. Two unauthenticated requests to the public embed and oEmbed pages (code under `/spikes/t03d/`, not merged).*

## Question

How can the self-hosted server read the track list of a **public Spotify playlist** from its URL (title, artists, album, duration, ISRC if possible), for personal use, as of October 2026? The answer feeds RF-08 and T11. ISRC matters because it makes matching to YouTube Music (and MusicBrainz) far more reliable than title/artist text.

## What changed at Spotify (the short version)

| Date | Change | Effect on us |
|---|---|---|
| 2024-11-27 | New apps lose related artists, recommendations, audio features, featured/category playlists; **Spotify-owned (editorial/algorithmic) playlists** return 404/filtered for non-extended apps. | Editorial playlists ("Today's Top Hits", "Discover Weekly") are unreadable by any app we could register. |
| 2025-05-15 | Extended quota mode reserved for "established, scalable, and impactful use cases" (in practice, businesses). | A self-hosted project will never leave development mode. |
| 2025 (Feb blog) | Insecure redirect URIs removed: HTTPS only, except loopback `127.0.0.1` / `[::1]`. | OAuth callback needs HTTPS (Tailscale serve is fine) or a loopback address. |
| **2026-02-11** | New development-mode apps: **owner must have Premium**, 1 Client ID (raised to **25** in July 2026), **max 5 authorized users**, reduced endpoint set. `GET /playlists/{id}/tracks` removed → `GET /playlists/{id}/items`, **only for playlists the user owns or collaborates on**. `GET /playlists/{id}` returns metadata only (no `items`) for other playlists. Batch `GET /tracks?ids=` removed. Spotify is "moving away from the Client Credentials flow for metadata endpoints". | Reading **someone else's public playlist through the official API is no longer possible** for a new app, with any flow. |
| 2026-03-09 | The restrictions apply to existing dev apps too; the **endpoint** part was postponed for *existing* integrations (no new date). New Client IDs stay fully restricted. | Any admin installing UltimateTunes registers a *new* app → full restrictions. |
| 2026-03 | `external_ids` (ISRC) on tracks/albums **reverted**: still returned. | ISRC available wherever we can read the track. |
| 2026-07 | Dev-mode quotas counted **per developer account**; quota exhaustion returns 429 with `reason: QUOTA_EXCEEDED`. | One admin account = one shared quota. Fine for personal use. |

## Recommendation

1. **v1 (T11): file import is the Spotify path.** `POST /ut/v1/imports` accepts an uploaded CSV/JSON besides a YouTube Music URL. Supported formats: Exportify CSV (ISRC used first for matching, then title/artist/album/duration), Spotify "Download your data" playlist JSON, and a documented generic CSV. No outbound Spotify request, no credentials, nothing for the admin to configure. Always available.
2. **Spotify URL import via the Web API (option b) is optional and off by default.** It only serves playlists the user owns or collaborates on, needs a Premium app owner, a 5-account allowlist, an OAuth callback and stored refresh tokens. Worth it only if the author wants one-click import of their own playlists. Proposed as a later, separate task (or a stretch goal of T11 after the coordinator adds the contract for the OAuth callback), hidden unless the admin configures it, as RF-08 already says.
3. **Rejected:** client credentials (a) — cannot return playlist contents any more; embed/scraping (c) — breaks Spotify's User Guidelines, no album/ISRC, fragile, outside the host allowlist.

## What the admin configures

- Option d (v1): nothing.
- Option b (if built later): register an app at developer.spotify.com with a Premium account; set redirect URI to the server's HTTPS URL (Tailscale serve) `…/ut/v1/spotify/callback` or a loopback address; add each user's Spotify account e-mail to the app's allowlist (max 5); give the server `UT_SPOTIFY_CLIENT_ID` and `UT_SPOTIFY_CLIENT_SECRET` (env or Docker secret). Without both, the option is hidden.

## Hosts contacted (allowlist)

- Option d: **none**.
- Option b: `accounts.spotify.com` (token exchange/refresh; the browser, not the server, visits the authorize page) and `api.spotify.com` (`/v1/me`, `/v1/me/playlists`, `/v1/playlists/{id}`, `/v1/playlists/{id}/items`). Import URL allowlist for Spotify: `open.spotify.com` only (parsed locally to extract the playlist id, never fetched).
- Never: `open.spotify.com/embed`, `oembed`, web-player internal APIs.

## Proposed SPEC §11 decision text

- **Spotify playlist import** (2026-10-12, T03d): since Spotify's February 2026 development-mode changes, no app we can register reads the contents of another user's or an editorial playlist (client credentials returns no items; user login only reads playlists the user owns or collaborates on; extended quota is reserved for businesses). Scraping the embed page breaks Spotify's User Guidelines and is rejected. v1 imports Spotify playlists from an **uploaded file** (Exportify CSV with ISRC, Spotify data-export JSON, generic CSV) and contacts no Spotify host. Importing by Spotify URL through the Web API (Authorization Code, owned/collaborative playlists only, Premium app owner, max 5 allowlisted accounts) stays optional, hidden unless the admin configures client id/secret, and is not part of T11 unless the coordinator adds it. RF-08 and T11 to be reworded accordingly.
